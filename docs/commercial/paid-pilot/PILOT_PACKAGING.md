# Paid Pilot Packaging

## Packaging principles

Packages are commercial planning boundaries, not security tiers. Every package uses the same non-negotiable controls: tenant isolation, least privilege, audit logging, evidence provenance, certified origin controls where applicable, human analyst authority, and fail-closed behavior.

The order form is authoritative for limits, dates, service levels, fees, and included integrations. The placeholders below must be replaced only from the approved price card.

## Package comparison

| Dimension | Starter Pilot | Professional Pilot | Enterprise Pilot |
|---|---|---|---|
| Intended use | One bounded workflow | Several related workflows | Cross-team or integration-heavy validation |
| Users | Up to `[approved limit]` named users | Up to `[approved limit]` named users | `[Approved cohort and role limits]` |
| Environments | One approved non-production or controlled environment | Approved staging environments for the scoped workflows | Customer-approved environments listed in the order form |
| Integrations | `[Approved integration set]` | `[Approved integration set]` | Security-reviewed integrations and change plan |
| Evidence volume | `[Approved event/evidence limit]` | `[Approved event/evidence limit]` | Capacity and retention documented per order form |
| Support | Standard pilot support and scheduled reviews | Named operating contact and recurring review | Coordinated technical, security, and executive cadence |
| Reporting | Closeout scorecard and evidence summary | Weekly scorecard plus closeout report | Weekly, control, executive, and closeout reporting |
| Duration | Short option | Standard option | Extended option or staged phases |
| Pricing model | Fixed pilot fee or approved subscription minimum | Scope-based pilot fee plus approved services | Custom scope, services, and expansion pricing |

## Package selection rules

Select the smallest package that can answer the customer’s agreed validation question. Upgrade only when a documented requirement cannot be met within the current scope and the security, legal, and commercial impacts are approved.

Do not use package names to imply a security certification, product performance level, or guaranteed result. Package differences may change support and scope, but never permit weaker controls.

## Scope record

Each proposal must capture:

- Pilot package and version.
- Customer, tenant, sponsor, and accountable security owner.
- Named users and roles.
- Environments, data classes, integrations, and evidence limits.
- Start/end dates and review cadence.
- Support commitments and escalation path.
- Fees, payment terms, approved credits, and renewal treatment.
- Success criteria, stop conditions, and closeout decision owner.

## Upgrade triggers

An upgrade conversation may be opened when the customer requests additional users, workflows, environments, evidence volume, integrations, support, or reporting. It is not a success claim. The request must be logged, priced, security-reviewed, and approved before scope changes.
