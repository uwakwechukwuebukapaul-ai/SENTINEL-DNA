# Local Two-Human Staging Authority Ceremony

**Scope:** staging only
**Status:** `IMPLEMENTED — NOT YET DEPLOYED / NOT YET ENROLLED`

## Purpose and exact release

This coordinator supports a same-machine ceremony in which two distinct authenticated Sentinel DNA application principals approve one exact staging authority payload in sequence. It does not perform authority enrollment automatically.

The ceremony is bound exactly to:

- commit `0f734c3341799b93e8a66397f1a1da782fd3869d`;
- repository tree `42ba7a2e55a88029df2f9af0ea1812696a9d05ea`;
- image digest `sha256:34f610a61e02483b1d30c666d69d94452b27ea71c0feaca162c0e2e2df25d0f6`;
- database target `postgresql://sentinel@postgres:5432/sentinel_dna`;
- environment `staging`.

## Ceremony flow

1. Human A authenticates with an active account and completes existing MFA.
2. The server derives Human A's tenant from the authenticated session and requires it to match the ceremony control tenant.
3. Human A creates and confirms the exact release, authority ID, and control tenant.
4. Human A submits a requester public key, fingerprint, and detached Ed25519 signature over the complete canonical payload, including the reviewer binding.
5. Human A approves only the requester side and logs out.
6. Human B starts a fresh session, authenticates independently with MFA, and confirms the same release and tenant.
7. Human B submits the reviewer key and detached signature. The server verifies the signature immediately and requires the requester binding to match.
8. Only the reviewer may finalize. Finalization reconstructs the canonical payload and re-verifies the complete envelope with `StagingAuthorityArtifactVerifier`.
9. The coordinator returns an offline-verifiable artifact. Enrollment remains a separate operation.

Every mutation requires CSRF, a valid MFA-backed session, an active non-expired ceremony, server-side role enforcement, tenant authorization, and exact release confirmation. Client-supplied tenant and environment values are never authoritative.

## Hardened security controls

- Tenant identity is resolved from the authenticated server-side principal. Creation, requester approval, reviewer approval, finalization, cancellation, and relevant reads are tenant-scoped and fail closed across tenants.
- The coordinator operates only when the actual runtime environment is `staging`; production, development, test, unknown, and missing environments are rejected regardless of request JSON.
- Migration 013 creates the ceremony namespace only for explicit staging opt-in. Migration 014 independently enforces the same staging-only runtime guard before adding approval-binding columns.
- Requester and reviewer overlap is rejected for user ID, actor ID, provider subject, credential ID, MFA-session hash, key ID, and public-key fingerprint.
- Approval signatures are verified at submission using the existing canonical payload hash and Ed25519 signature domain. Finalization re-verifies both signatures, manifest digest, fingerprints, timestamps, release binding, and staging database target with `StagingAuthorityArtifactVerifier`.
- Each approval stores a signed payload hash and counterparty binding. The final artifact contains `artifact_integrity_hash`, which canonically binds the ceremony ID, artifact hash, approval evidence, and verification metadata. Any alteration causes offline verification failure.
- Expiry is transitioned atomically to terminal `EXPIRED`; cancellation and finalization are terminal, and duplicate/replayed transitions are rejected.
- Approval audit events include approval ID, ceremony ID, role, key ID, public-key fingerprint, hashed MFA-session reference, and exact release-binding hash. Raw MFA tokens, passwords, TOTP secrets, private keys, and unnecessary personal data are excluded.

## Trust boundary and identity limitation

The system proves two distinct authenticated application principals, sessions, credentials, cryptographic keys, signatures, and tenant memberships. It does **not** prove that two separate real-world humans controlled those principals. Same-machine use is acceptable, but one person controlling two accounts or keys must not be represented as independently proven two-human authorization.

The ceremony requires pre-existing active accounts with MFA and canonical membership. It is not a first-authority bootstrap mechanism.

## Key custody and offline evidence

Production or long-lived signing keys are not generated by the coordinator. Human A and Human B control their Ed25519 private keys outside the application. The application receives only key identifiers, public keys or references, fingerprints, and detached signatures. Private keys never enter the database, HTTP body, logs, audit records, Git, Docker configuration, or final artifact.

The final artifact contains the ceremony ID, canonical payload, manifest, requester/reviewer signatures, public-key resolver material, payload artifact hash, approval evidence, verification metadata, and `artifact_integrity_hash`. `verify_final_artifact()` validates it without the application database.

## Failure and deployment boundaries

The ceremony fails closed for missing, duplicated, mismatched, expired, cancelled, altered, or replayed approvals. A missing requester or reviewer approval prevents finalization, and no route performs enrollment automatically.

The migration namespace is staging-only and explicitly opt-in. Do not apply it to live staging during development. Do not run Docker Compose, enrollment, bootstrap provisioning, or container lifecycle operations as part of testing this coordinator.
