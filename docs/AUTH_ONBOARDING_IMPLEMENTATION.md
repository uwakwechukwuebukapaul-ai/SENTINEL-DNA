# Sentinel DNA Authentication, Onboarding, and Security Implementation Report

Date: 2026-09-02
Status: Engineering work in progress; not a Gate 5 completion claim.

## 1. Existing architecture

The repository audit found an existing canonical authentication boundary in
`services/auth/routes.py`, `AuthService`, Flask signed sessions, persistent-session
revocation, Google OIDC, provider-neutral email/SMS delivery, canonical tenant/identity/
membership authority, pilot authorization, audit infrastructure, and a tenant-scoped
analyst workspace. The authoritative WSGI path is `wsgi.py` -> `app.create_app()`.

## 2. Reused and modified components

Reused: `AuthService`, `GoogleOIDC`, auth providers, `SecurityContext`, canonical
authority, permission/pilot boundaries, existing audit services, investigation
coordinator/projection/report services, and the registered browser workspace.

Earlier working-session modifications already present in this dirty tree include the
premium authentication templates/assets, canonical tenant-scoped dashboard snapshot
integration, generic dashboard error handling, and Gate 5 private-access configuration/
validator changes. Those changes are preserved and must be validated against this audit.

No new authentication service, tenant architecture, session stack, or audit system has
been authorized.

## 3. Newly implemented versus still required

The current tree includes an authentication shell and frontend interactions for login,
signup, OTP, searchable country selection with flag labels, password strength, recovery,
loading/error states, cooldowns, and reduced motion. It also includes safer generic error
handling and canonical dashboard data usage.

Server-side changes add `users.onboarding_state`, validated lifecycle transitions,
session-bound registration/login/recovery OTP challenges, and atomic conditional OTP
consumption. Browser registration advances only after server-side email/phone proof and
does not accept client role or tenant values.

Still required before security completion: a complete user-facing resume and
self-service provisioning retry contract, idempotent registration/provisioning semantics,
the canonical `SOC-L1` decision, complete adversarial tests, real browser acceptance,
and approved production provider configuration.

## 4. Security improvements and preserved controls

- Secure session configuration, session rotation/clear on login, session version
  invalidation, persistent token hashing, revocation, CSRF, rate limiting, scrypt
  password hashing, generic auth errors, and fail-closed production provider behavior
  remain in the existing architecture.
- Dashboard tenant identity continues to come from canonical authenticated context.
- Client role/tenant inputs are not accepted as registration authority.
- No public network path, Cloudflare dependency, broad firewall rule, secret, private key,
  or TLS-verification bypass was introduced by the documented architecture.
- Gate 5 human pilot evidence is not generated by this report.

## 5. Authentication/OAuth/OTP

Password login, logout, recovery, email OTP, phone normalization, and Google OIDC remain
under `/api/auth`. Google validation uses provider subject, state, nonce, issuer,
audience, signature, time, and verified-email checks. Phone verification is currently
treated by the inspected architecture as onboarding/account verification, not MFA; no
MFA claim is made until product policy and a step-up implementation support it.

OTP storage is hashed and purpose-bound with expiry, attempt count, single-use state, and
cooldown. Atomic conditional consume and browser-flow binding are implemented; full
concurrent operational evidence remains to be measured.

## 6. Database, API, RBAC, tenant/workspace, and audit impact

The implementation uses additive runtime schema evolution in `AuthService` for
`users.onboarding_state` and `otp_challenges.session_binding`; no destructive migration
or session invalidation was applied. Existing API routes and canonical tables are the
integration boundary. The existing role vocabulary is
`admin`, `soc_manager`, `analyst`, and `viewer`; the required `SOC-L1` label conflicts
with that vocabulary and is unresolved. No role semantics were silently changed.

Existing canonical tenant/membership and pilot provisioning are preserved. Existing
auth/pilot/audit event conventions remain authoritative. Any additive state table or
index must be separately documented with migration/backfill/rollback before use.

## 7. Frontend/UX

The authentication shell uses deep navy/black surfaces, Sentinel blue/cyan indicators,
restrained evidence-node geometry, precise typography/spacing, accessible focus states,
touch-safe responsive controls, country selection with Nigeria support, OTP focus/paste
behavior, password-strength progression, loading/error states, and reduced-motion rules.
No unsupported compliance or certification claims are presented.

Actual in-app browser acceptance could not run because the browser runtime reported
`No browser is available`; visual/browser claims remain engineering inspection only.

## 8. Environment, migration, and rollback

Existing runtime configuration is defined by `config/runtime.py` and environment examples
including secure cookies, pilot access, tenant isolation, audit logging, Google provider
variables, and email/SMS provider selection. Production and staging provider adapters remain required
and are intentionally not replaced by test/console delivery.

No migration has been applied for this audit. A future additive onboarding migration must
be deployed schema-first, backfilled only from verified records, rolled out compatibly,
and reversible by disabling new transitions without deleting old identity/session data.

## 9. Tests and baseline

Baseline evidence is recorded in `docs/AUTH_ONBOARDING_AUDIT.md`. The earliest available
Node baseline was 88 total with 86 pass and 2 trusted-browser environment failures. The
dashboard Python baseline reached 100% assertion output but hung during teardown and was
interrupted. The browser runtime was unavailable.

Post-edit focused Python results already observed:

- `py -3 -m pytest tests/dashboard/test_auth_experience.py tests/security/test_logout_navigation.py tests/staging/test_staging_security_contract.py -q` -> `32 passed`.
- `py -3 -m pytest tests/auth tests/dashboard tests/security/test_analyst_demo_workflow.py tests/security/test_logout_navigation.py tests/staging/test_staging_security_contract.py -q` -> `125 passed, 4 skipped`.

These are not a substitute for the complete before/after regression comparison. Node
contracts, adversarial auth tests, staging validator tests, and full regression still
require a final bounded run and classification of environment hangs/failures.

## 10. Browser acceptance

Not measured. The in-app browser was unavailable. Therefore the following remain
NOT_MEASURED: real new-user registration through dashboard, returning-user login through
dashboard, incomplete onboarding resume, direct dashboard denial in a browser, mobile
layout, keyboard/focus/OTP/country-selector acceptance, and no-JavaScript-error evidence.

## 11. Threat-model result

The threat model is in `docs/AUTH_ONBOARDING_THREAT_MODEL.md`. Existing controls are
strongest at the session, canonical context, pilot boundary, OIDC claim-validation, and
now atomic/session-bound OTP layers. The unresolved high-impact items are user-facing
resume/provisioning idempotency, role vocabulary, and real browser/operational evidence.

## 12. Remaining production and Gate 5 blockers

- No human approved-analyst pilot evidence is claimed.
- Tailscale operational success from the Samsung S10 must be observed and recorded; a
  same-host test is not equivalent to the approved-device observation.
- External tailnet policy/custody evidence must exist at absolute paths; the validator
  correctly fails closed when policy is missing.
- Fresh staging backup, isolated restore evidence, and human release/security approval
  remain required.
- Production email/SMS provider configuration and Google redirect configuration remain
  deployment responsibilities and must not be placed in the repository.
- Durable onboarding, `SOC-L1` role decision, atomic OTP race handling, and adversarial
  coverage remain unresolved.

## Gate status

- Dashboard acceptance: **CONDITIONAL** — focused server-side tests pass, but browser
  acceptance is unavailable and onboarding/security gaps remain.
- Tailscale operational readiness: **CONDITIONAL** — the private architecture is
  configured and local TLS/DNS checks pass, but approved-device reachability and external
  tailnet policy evidence are not complete.
- Gate 5 overall: **NOT COMPLETE / NOT HUMAN-PILOT COMPLETE**.
